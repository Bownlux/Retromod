# Mojang names that more than one intermediary class maps to (task: recycled-name audit).
#
# A collision is usually legitimate. Fabric renumbers intermediary ids across versions, so the same
# logical class can carry an old id and a new one, and both must resolve to the same Mojang name or
# a mod built against either version stops working. Every entry below was checked that way.
#
# A collision is a BUG when the two ids are genuinely different classes on 1.21.11, the last version
# intermediary covers. That happens when Minecraft renames a class and then reuses the old name:
# the old Cow became AbstractCow and a new Cow appeared under it. Mapping both ids to the new name
# means a mod that meant the base silently links against the leaf. 37 rows were in that state.
#
# IntermediaryDestinationCollisionTest enforces this list EXACTLY:
#   - a NEW entry fails the build. Resolve it by joining Fabric intermediary to the Mojang
#     mappings for 1.21.11 and pointing each id at the class it actually became. Add it here only
#     if the two ids really are the same logical class under different intermediary numbering.
#   - a REMOVED entry also fails, so a fix has to update this file deliberately.
#
# Regenerate the evidence with the loom intermediary tiny plus the 1.21.11 client mappings; a jar is
# not needed to run the test, only to decide what belongs here.
#
# 1.4.0-snapshot.3 added older keys for classes whose outer class moved or was replaced while
# the class itself stayed: GlStateManager's state inners under platform/ and opengl/ keep their
# inner ids, LookAtEntity kept class_9251 when it moved from TeleportCommand to LookAt, and
# BlockStateModelLoader$ModelGroupKey follows the ModelGroupCollector$GroupKey move in
# mojang-class-moves-26.1.tsv.
