# Loader API Runtime: Maintainer Notes

The loader API runtime serves old loader API calls on new hosts. The first piece is old Fabric API on Fabric and Quilt hosts for Minecraft 26.1 and newer. This note covers the foundation (batch B0) and what each later batch builds on.

## Setting

`loader_api_runtime` is `auto`, `true` or `false`. Precedence, highest first: `-Dretromod.loaderApiRuntime`, the CLI flag `--loader-api-runtime`, the config key (in game only), then `auto`. `auto` is on when `RetromodVersion.isSnapshotBuild` is true. A provider can graduate with `LoaderApiProvider.graduatedIn`, after which `auto` turns it on in every build from that release. The hook gates per provider, so a graduated provider runs in a stable build while the others stay off. An explicit `false` never loads a provider.

The startup line names the switch that works where Retromod runs: the system property when it decided, `--loader-api-runtime=false` in the CLI, and the config key in game.

The Maven test suite pins `retromod.loaderApiRuntime=false` in surefire, so the same commit passes before and after an rc bump. Runtime-on tests turn it on through `LoaderApiTestSupport.runtimeOn`.

## Ownership

`RetromodTransformer.claim(RedirectKey)` clears every table entry for a key, side tables included, and turns later registrations for it into DEBUG no-ops outside an owned scope. `suppress(RedirectKey)` claims a key and leaves the host's own member in place. A type key covers every member keyed on that type. A method claim also removes a name-only rename on the same owner and name. `resetOfflineRegistrations` clears claims and moves `registrationEpoch()`.

Providers never call the transformer's register methods for an unclaimed key. `LoaderApiRegistration` has helpers that claim first (`redirectMethod`, `redirectInherited`, `redirectClass`, `redirectField`, `retypeLambda`, `replaceImplementedInterface`, `registerPerModSynthetic`).

## The Hook

`LoaderApiRuntime.prepare(transformer, context)` is the single registration hook. It is idempotent per registration epoch and context. Callers:

- `RetromodPreLaunch`: after shims, AutoFix and polyfills, before any transform.
- `Retromod.onInitialize`: after it registers shims and polyfills again, before AOT.
- `FabricModTransformer.transformMod` (Quilt goes through it), `AotCompiler.compileJar`, `FullAotCompiler` (`prepareForProcess`), `ApiEmbedder.embedRequiredShims`, and the CLI `transformJar`.
- `RetromodTransformer.transformClass` runs it again through `PreTransformHook` when something cleared the rows. The hook exists only after one of the callers above ran `prepare` on that transformer. The javaagent alone never runs it, because it knows neither the loader nor the host.

Within one registration epoch, a context for another loader (a Forge jar through AOT, `ApiEmbedder` without metadata) adds to the rows already registered instead of replacing them. A context for the same loader on another host releases that loader's earlier rows first. After a reset, the hook registers every context again in its first order.

`LoaderApiWiringTest` fails when a call is removed. `LoaderApiOwnershipTest` replays the pre-launch, onInitialize, GUI, CLI, batch, AOT and full AOT orders.

## Rows and Data

- `src/main/resources/retromod/loaderapi/fabric-26x/renames.tsv`: renames and pinned redirects, keyed by 26.x Mojang descriptors, with a host range and call-site owners for calls made through a subtype. Kind `D` sends an instance call to a static helper that takes the receiver first. A two-part `host_to` such as `26.1` covers the whole line. Bump `rows_version` whenever a row changes. The version is part of every translated jar's identity. Rows version 2 pins `FabricLoader.getModContainer` to `VersionSpoofer`, where version 1 suppressed it and so dropped version spoofing. Rows version 3 adds batch N1. Rows version 4 sends `PacketType.create` to `TypedPackets.createType` and adds `LoginPacketSender` as a call-site owner of the two `PacketSender` listener rows. Rows version 5 adds batch R1. Rows version 6 sends the two section layers 26.1 removed to their successors (R1). Rows version 7 adds batch S1. Rows version 8 matches each field row also where a mod reads the static field through its own subtype, and gives mod sub-interfaces of `HudRenderCallback` the old methods (S1 review). `RowsVersionDigestTest` keeps a digest of what the runtime registers on each indexed host, by rows version, in `src/test/resources/loaderapi/fabric-26x-registration-digests.tsv`, and fails when the registration changes and the version does not. Add a block for each new version and keep the older ones.
- `surface-26.1.tsv` to `surface-26.4.tsv`: the host Fabric API signatures, as the intersection of the builds listed in each header. Regenerate with `scripts/loader-api-surface.py` and check with `--check`. 26.4 is indexed so the coverage test can catch a row that works on 26.3 but not on the newest host.
- `docs-dev/loader-api/fabric-26x-status.tsv`: hand-kept facts per old member (impossible reasons, dev-only marks, batch, evidence). It was seeded from the 2026-10-16 design data, without the 21 rows that came from Retromod's own output and with the call-site owners of 12 rows reached through a subtype.

## Translation Identity

A translated Fabric jar carries `Retromod-Loader-Api-Runtime: fabric-26x/<rows version>` while the runtime is on. AOT cache stamps get `|loaderApi=fabric-26x/<rows version>` and the per-jar AOT context gets the same suffix. At pre-launch, `FabricTranslationIdentity` rebuilds every jar in `mods/` whose identity differs from the current one, from its original in `retromod-input/processed/`, and asks for the restart. Fabric has loaded the old jar by then, so the rebuild goes to `retromod-input/pending/` and a shutdown hook moves it over the old jar. Where that move fails on Windows, the hook sets the DOS hidden flag on the old jar, which Fabric's directory scan skips. The next pre-launch installs the waiting copy into the hidden or missing slot and asks for one more restart. A waiting copy whose old jar is still loaded is scheduled again without a restart prompt, and a copy that no longer matches the setting is deleted. On Windows, a hidden translated jar whose waiting copy is gone is shown again, so the mod does not vanish. The Windows path is not verified on Windows yet.

## Link Check

With the runtime on, the runtime, CLI and AOT paths log the Fabric API references a translated jar still makes that the host lacks, once per jar. The check reads the jar that ships: the runtime path after it repackages, the CLI and AOT paths after `SyntheticEmbedder` has embedded the jar's synthetics. Each jar in `META-INF/jars/` is checked too and named after its parent, as in `mod.jar > META-INF/jars/lib.jar`; a mod and its nested jars count as one set of types, because Knot loads them side by side. A bundled Fabric API module (`fabric-*.jar`) is skipped, because the host's own module replaces it and the runtime path strips it. A lambda is checked by its interface and by its interface method, because the host calls the interface's own method, so a lambda built on an old method never runs. A reference to another mod's type is not checked.

Helper methods and public fields that translated jars name are append-only within the 26.x line. `LoaderApiHelperAbiTest` compares both with `src/test/resources/loaderapi/helper-abi.txt`, fields as `owner.name:descriptor`.

## Types That Cross a Mod Boundary

A type a library can expose in a public signature (`BlockColor`, old SAM interfaces, holders) must have one name per process. `BoundaryTypeSpec` maps the old name to a compiled interface in a `.../shared/` package under `com/retromod/loaderapi/` with `Object` parameters. It retypes lambdas, sends typed calls to the erased method, and gives implementing classes and interfaces a per-mod bridge interface.

The erased method has its own name on every shared type (`receiveServerPlayChannel`, `writeLegacyPacket`), never the old method's name, and `BoundaryTypeSpec` refuses a second shared type with the same erased name and descriptor. One class can then implement several shared types of one shape. Each class that names a bridge in its interface list also gets a concrete erased method from `RetromodTransformer.registerImplementedMethodBridge`. A class method wins over interface defaults, so a class that reaches two jars' copies of one bridge, such as a dependent's handler that extends a library's handler and names the old type again, still has one method to run. A mod interface that extends the old type keeps the bridge's default, for its lambdas. A class that implements two such interfaces from two different jars, and names neither the old type nor a handler class, still sees two defaults and fails when called. `BoundaryTypeTwoJarTest` translates a library and its caller separately and runs them together, including both of these shapes. Compiled helpers and shared types extend only JDK or Retromod types (`LoaderApiOfflineLoadTest`).

## Coverage

`retromod loader-api-coverage --hosts 26.1,26.2,26.3` (or through `mvn exec:java`) replays registration per host with the runtime forced on and writes `target/loader-api-coverage/fabric-26x.{tsv,json,md}`. `src/test/resources/loaderapi/fabric-26x-baseline.json` holds the done rows; a batch updates it in the same change. With `--usage ranked-members.tsv`, a row gets `old_mods` from its own key and `call_site_mods` from the keys of its call-site owners. The outputs carry both, plus `reach_mods`, their sum, which counts a mod twice when it calls both ways. Rank a worklist by `reach_mods`, so rows reached only through a subtype do not sort as unused. Usage keys that resolve on neither the host surface nor a status row go to `fabric-26x-unmatched.tsv`. A row the status table marks impossible stays impossible when the runtime claims only its owner type, as S1 does for the pre-1.20 shapes of callbacks whose newer shapes it serves; a row whose own key the runtime declares is classified by its target.

## Batch N1: Play-Channel Networking

N1 serves the old raw play channels (an `Identifier` plus a `FriendlyByteBuf`), the old typed packets (`FabricPacket` and `PacketType`, in play and in the 1.20.2 to 1.20.4 configuration phase), the old `PacketSender` sends with either listener type, and the 1.20.5 to 1.21.11 `createS2CPacket` and `createC2SPacket` names. It takes over the client raw channels the old bridge used to serve, so both sides behave the same way. `NetworkingRows` registers the shared types and helper owners; the call rows are in `renames.tsv` with batch `N1`.

Each channel id gets one raw payload type in `PayloadTypeRegistry`. A receiver registers its channel in both directions of its phase, and `PacketType.create` registers both play directions, because Fabric API keeps payload types in a plain `HashMap` that connection threads read and expects them before the first connection. Mods do both of these at startup. A channel that only this side sends on is registered at its first send, during play, and the first such channel is logged at info level, later ones at debug. The payload and codec are `RawChannelPayloads`, which the old client bridge uses too. A channel already registered with that codec, by the old bridge or a jar translated earlier, is shared. A channel another mod registered with its own payload type is left alone: the old mod's receiver is not registered and its packets on that channel are dropped, each with one log line. A packet built on such a channel (`createS2CPacket`, `createC2SPacket`, `PacketSender.createPacket`) carries a `DiscardedPayload` on `retromod:discarded`, which no registry knows, so it encodes as its id alone and the other side ignores it; the other mod's codec could not write Retromod's payload, and that failure would disconnect the player. A send to a side that has no receiver for the channel is dropped with one log line, because the payload would only be discarded there.

Handlers run through the host's typed receivers, on the game thread, where old channel handlers ran on the netty thread. The response sender's phase and direction come from the context the runtime handed out, else from Fabric API's addon class name. A `LoginPacketSender` keeps raw login queries. The old handler interfaces, `FabricPacket` and `PacketType` are shared types under `net/shared/`; `ServerConfigurationNetworking$ConfigurationPacketHandler` kept its name on 26.x with a new method, so an old handler of that type is called by reflection. While the runtime is on, `ClientPlayNetworkingV1Bridge` forwards to `LegacyChannels` through `RawChannelPayloads.ClientDelegate`, and the polyfill `FabricNetworkingBridge` (the server and client raw-channel bridge of jars translated without the runtime) forwards through `FabricNetworkingBridge.Delegate`. `LegacyChannels.installOldBridgeDelegates` installs both. A lambda from such a jar implements only the old typed `receive`, because that translation never retyped it to the bridge interface's `Object` method, so the runtime calls the method the lambda has. While the runtime is off, both bridges behave as before.

`PacketSendListener.thenRun` and `exceptionallySend` are Minecraft members, but 26.x turned the interface into a class whose factories return a netty listener, and Cardinal Components 6 sends with them. N1 maps them to `SendListeners`, which returns a plain `PacketSendListener` that stands for the host listener, so the mod's checkcast still passes. The stand-in works only where it reaches a redirected `PacketSender` member. Vanilla members that took the old listener, such as `Connection.send(Packet, PacketSendListener)` and the configuration listener's `send`, and the old instance methods `onSuccess` and `onFailure`, still fail on 26.x; Essential 1.5.1 for 1.21.1 calls them from its nested jar. Forge and NeoForge mods get none of this, because it lives in the Fabric runtime. A loader-agnostic Minecraft shim would serve every loader, but it would change translated output while the runtime is off, which this project keeps identical to the build before the runtime.

Limits. Both ends need Retromod with the runtime on, because raw bytes now travel inside a payload type. A channel that only this side sends on is registered at its first send, while players may be connected, and a packet another mod sends at that instant can fail to encode; a real fix needs the channel ids before the first connection, which old mods never declared. A native mod that registers a channel id after an old mod already used it fails in its own initialization, as Fabric API fails any duplicate; the reverse order is handled. The 1.20.2 to 1.20.4 shapes (typed configuration packets, `createS2CPacket(FabricPacket)`, `createC2SPacket(FabricPacket)`, `PacketSender.createPacket(FabricPacket)` and `sendPacket(CustomPacketPayload, GenericFutureListener)`) have unit tests only, because neither test mod can compile them and no corpus mod calls them. Client rows need a client run of `Test38ClientChannelEcho` and `Test40ClientPayloadPacket` before they count as done.

Tests: `NetworkingRowsTest` (every row as a call, also through each call-site owner, lambda, override, type reference and subtype, checked against the 26.1, 26.3 and 26.4 surfaces, then loaded on the fake host so the JVM verifier checks it and each shared handler method it implements runs), `LegacyChannelsTest` and `TranslatedModOnFakeHostTest` (a fake 26.x server and client in one JVM, compiled from `src/test/resources/loaderapi/fakehost/`), and `HostMembersTest` (every host member the helpers call). Test-mod cases: Test35 to Test38 in the 1.20.1 mod, Test39 and Test40 in the 1.21.1 project.

## Batch R1: Block Render Layers and Color Providers

R1 serves the old `blockrenderlayer.v1.BlockRenderLayerMap` (its `INSTANCE` and every `put`), the static `client.rendering.v1.BlockRenderLayerMap` that 1.21.6 to 1.21.11 mods call (defect D6), and `ColorProviderRegistry.BLOCK` and `ITEM`. The vanilla `BlockColor` and `ItemColor` callbacks those registries take were removed in 26.1, so they become the shared types `LegacyBlockColor` and `LegacyItemColor`. Balm declares `BalmRenderers.registerBlockColorHandler(BlockColor, Supplier)` and Waystones calls it; translated apart, both name `LegacyBlockColor`. The two registry types become the shared interfaces `LegacyBlockRenderLayerMap` and `LegacyColorProviderRegistry`. `RenderRows` registers the shared types and the two removed section layers; the class and call rows are in `renames.tsv` with batch `R1`. The runtime also claims the no-op stand-in `com/retromod/generated/legacyfabric/BlockRenderLayerMap` that both map types used to point at. No Fabric API code is adapted: the contracts come from `fabric-rendering-v1` and `fabric-blockrenderlayer-v1` 0.92.12+1.20.1, and the host side from the 26.1.2 and 26.3 jars.

Render layer calls are recorded in `LegacyRenderLayers` and change nothing on the host. 26.1 and newer bake each quad into the solid, cutout or translucent section layer from the alpha of the texture area it uses (`FaceBakery.computeMaterialTransparency` to `ChunkSectionLayer.byTransparency`), and `FluidModel` does the same for fluids. This was read from the 26.1.2 and 26.3 client jars, not seen in a game. A block whose old layer was translucent but whose texture has only opaque and fully clear pixels renders as cutout. On a client, Retromod's Minecraft side maps the old `RenderType.solid()`, `cutout()`, `cutoutMipped()`, `translucent()` and `tripwire()` getters to the `RenderTypes.*MovingBlock` tokens, so a recorded instance-map layer is one of those; the 1.21.6 static form records the real `ChunkSectionLayer`.

The static form passes a `ChunkSectionLayer`, and 26.1 kept only `SOLID`, `CUTOUT` and `TRANSLUCENT`. A read of `CUTOUT_MIPPED` (`field_60924`, 1.21.6 to 1.21.10) goes to `CUTOUT`, and a read of `TRIPWIRE` to `TRANSLUCENT`, the layers that took over their blocks and the ones the old render type getters already map to. Without that, the read throws `NoSuchFieldError` in the mod's client setup before the layer call runs. Fabric API 0.128.2+1.21.6 identifies `field_60924`: its `RenderLayerHelper` maps the five constants in order to `getSolid`, `getCutoutMipped`, `getCutout`, `getTranslucentMovingBlock` and `getTripwire`, and no 1.21.6 to 1.21.10 intermediary jar is local. `CUTOUT_MIPPED` has no 26.x name in the intermediary table, so its read keeps the intermediary name after the remap and the redirect is keyed on it. Both redirects are Minecraft members registered by the Fabric runtime, so Forge and NeoForge mods do not get them.

Old block colors go to Fabric API's `BlockColorRegistry.register(List, Block...)` as 128 tint sources per block. Every indexed host has the host members R1 calls, from the 26.1 builds (Fabric API 0.145.1 and newer) through 26.4: that register method, `ModelLoadingPlugin.register` with `modifyItemModelBeforeBake`, and the Minecraft members `HostTintsMembersTest` lists. The `BlockTintsFactory` form, added within the 26.1 line, is not used for old colors, because it computes every tint index eagerly. Each asks the old provider for its own tint index, so a model may use tint indices 0 to 127; an index past that renders untinted (Traveler's Backpack uses 108). The host computes a tint only for an index a quad uses, so unused slots cost a list copy per tinted block. `color(state)` passes a null level and position, as the old contract allowed. Old providers returned RGB and old block renderers ignored alpha, while 26.x multiplies it into the vertex, so block colors are made opaque. `BLOCK.get` returns the provider an old call registered; for any other block it returns the host's tint sources as an old provider, and registering that result for another block reuses those sources.

Newer Fabric API builds also let a mod color a block with a `BlockTintsFactory`, and they refuse a static color for a block that has a factory and a factory for a block that has a static color, by throwing `IllegalStateException` into whichever mod registers second. This was read from `BlockColorRegistryImpl` in Fabric API 0.155.3+26.1.2, 0.158.0+26.2 and 0.162.0+26.3; 0.145.4+26.1.2 has neither the form nor the check. Old Fabric API never threw there. So on a host with `BlockColorRegistry.getFactory`, an old block color registered before the client creates its block colors waits until `ClientLifecycleEvents.CLIENT_STARTED`, when every mod has registered its factories, and then skips each block that has one, with one log line per block. The native mod's dynamic color wins and neither mod sees an exception. An old color registered after that is applied at once, with the same skip. A native mod that adds a factory after the client started still fails for a block an old mod colored, as it does for any block that already has a color. If the host refuses a color anyway, Retromod logs it and the old mod's client setup continues. Because old colors are applied after every mod's client setup on these hosts, an old color replaces a native mod's static color for the same block, as the later of two old registrations did. Where the host has no lifecycle events, old colors are applied at once. On a dedicated server, or a client without Fabric API, colors are kept for `get` only. The level type is client-only on 26.x, so a server cannot build a `BlockColor` lambda; old mods register colors on the client.

Item tints are item model data on 26.x. On the first `ITEM.register` on a client, Retromod adds one Fabric API model loading plugin whose item modifier gives a plain `minecraft:model` item model (`CuboidItemModelWrapper.Unbaked`) one tint source per tint index of its model, read from the model JSON and its parents (generated layers, or the face tint indices of the nearest model with elements). A model that cannot be read gets 4 slots. The host computes every slot on every frame, which is why the model decides the count. An item color with no alpha byte is read as RGB and made opaque, because 1.20 item colors had no alpha; a 1.21 color that carries alpha keeps it. Item models of another kind (`select`, `condition`, `composite`, special renderers) keep their own tints and log one line. An item color registered after the first model load applies at the next resource reload. `ITEM.get` returns only providers an old call registered, because vanilla item tints live in item models on 26.x.

Limits. The `ColorProviderRegistry` rows (the class, `BLOCK`, `ITEM`, `get` and `register`) and the static `client.rendering.v1.BlockRenderLayerMap` rows stay linked until a client run: `Test43ClientHostTints` for the host tint and `Test42` for the section layer constants. The 26.3 server runs only show that they link, because on a dedicated server Fabric API's rendering and model loading modules are absent, so `HostLink` finds no `BlockColorRegistry` and no model loading plugin, and the tests pass no section layer. The instance-form `blockrenderlayer.v1` rows count as done from the server runs, because their whole path is `LegacyRenderLayers`, which calls no host member; on a client only the recorded value differs. An in-game client has not checked any R1 rendering yet. Handcrafted 3.0.6 (1.20.1) and 4.0.3 (1.21.1), whose only Fabric API blockers were R1 rows, translate with no Fabric API reference left, but both stop on 26.3 before their client code runs, on the Minecraft side: `Seat` overrides `Entity.makeBoundingBox()`, which 26.x made final, and `KitchenHoodBlock.simpleCodec(Function)` is gone. Tiny Dragons and Critters and Companions, the other single-batch mods, were not available locally.

Tests: `RenderRowsTest` (every row as a call, field read, type use and implementing class, the static form with each of the five 1.21.6 section layers, and both color callbacks as a lambda, an override, a typed call, a mod sub-interface and calls through both subtypes, checked against the 26.1, 26.3 and 26.4 surfaces and loaded on the fake host), `TranslatedColorModOnFakeHostTest` (old mods translated through the CLI and run on the fake host: block colors reach the host by tint index, a host block's colors copy to a mod block, a baked item model gets the item color as tints, both render layer forms record, the removed section layers record as their successors, a native dynamic color keeps its block in either order, an old color waits for the client start and skips only dynamically colored blocks, and a library that takes `BlockColor` serves a mod translated apart), `RenderHelpersTest` (tint slots from model JSON, the alpha rules, and the side with no host) and `HostTintsMembersTest` (every host member the helpers call, on the 26.1 to 26.4 surfaces and in the local 26.1.2 and 26.3 client jars; `BlockColorRegistry.getFactory` from 26.2, because older 26.1 builds lack it). Test-mod cases: Test41 (common, both sides) and Test43 (client) in the 1.20.1 mod, Test42 in the 1.21.1 project, which compiles the 1.21.6 static calls against stand-ins its jar leaves out, including `CUTOUT_MIPPED` and `TRIPWIRE` on a client.

## Batch S1: HUD, Screen Render Events and Tooltips

S1 serves the old `HudRenderCallback` in its 1.20 and 1.21 shapes, the old screen render events (`ScreenEvents.beforeRender`, `afterRender` and their callback types), the three-argument `ItemTooltipCallback` and its deprecated v0 twin, the 1.21.4 and 1.21.5 HUD layer API (`HudLayerRegistrationCallback`, `LayeredDrawerWrapper`, `IdentifiedLayer`), the 1.21.5 to 1.21.8 `GatherDebugTextEvents`, and the `VanillaHudElements` ids 26.x renamed or removed. `ScreenRows` registers the shared types and the callback bridges; the call and field rows are in `renames.tsv` with batch `S1`. No Fabric API code is adapted. The contracts come from Fabric API 0.92.2 (1.20.1), 0.116.17 (1.21.1), 0.119.4 (1.21.4), 0.128.2 (1.21.5 and 1.21.6), 0.136.1 (1.21.8) and 0.141.6 (1.21.11), and the host side from the 26.1.2 and 26.3 jars.

`HudRenderCallback` becomes the shared `LegacyHudRenderCallback`, whose `EVENT` is one Fabric API event for every mod. One HUD element, `retromod:legacy_hud_render_callback`, draws it; the runtime adds it last to `HudElementRegistry` when the first old mod reads the event, because Fabric API 0.92.2 and 0.141.6 both drew these callbacks at the tail of the HUD render. A 1.21-shape lambda is built on `renderLegacyHud(Object, Object)`, a 1.20-shape lambda on `renderLegacyHudWithPartialTick(Object, float)`, which gets the frame's `getGameTimeDeltaPartialTick(false)`. A class keeps the method it was written with: the shared type finds it by its parameter types once per class and calls it through a method handle. So a class, a mod's own sub-interface and a library's base class all work, and there is no per-mod bridge that two jars could both bring. A call through a mod's sub-interface is matched by hierarchy, which only that mod's jar can prove, so each such sub-interface also gets two synthetic default `onHudRender` methods, one per shape, each forwarding to its erased method. A dependent's call through a library's sub-interface then links, and the shared type skips these bridges when it looks for a class's own method. A mod that fires the old invoker with a float reaches 1.21 callbacks through a delta tracker that answers that float. The per-mod `EVENT` and HUD element of `FabricHudRenderCallbackShim` (critique 12) and the stand-in `HudRenderCallbackShim` are claimed, so no translated class names them, and `Retromod.onInitialize` no longer adds `HudRenderCallbackShim`'s element, which never drew on 26.x, where the runtime serves the host.

`ScreenEvents.beforeRender` goes to the host's `beforeExtract` (D1: it went to a method that never existed) and `afterRender` to `afterExtract`. `ScreenEvents$BeforeRender` and `$AfterRender` become the host's `BeforeExtract` and `AfterExtract`, so a library and its caller name the host type. A lambda implements the host method directly. A class or mod interface that implements the old type gets a per-mod bridge that extends the host type and calls the old method, and each class also gets its own `beforeExtract` or `afterExtract`, which wins over two jars' bridge defaults. `HostSamSpec` generates both, and `ImplementedMethodBridge` can now pass a subset of its arguments for that.

`ItemTooltipCallback.EVENT` keeps the host's event (D2: a dummy event used to drop every callback, the 1.20.5 to 1.21.11 ones included). The three-argument callback of 1.16.5 to 1.20.4, and the v0 `event.client.ItemTooltipCallback`, which now names the host type, are served by the same `HostSamSpec`: a lambda is built as a per-mod bridge that extends the host callback and drops the tooltip context, then typed as the host type again by a per-mod wrap class. A class gets the bridge and its own four-argument method that calls its three-argument one. A mod that calls the three-argument method itself, usually on the event's invoker, goes to `LegacyTooltips.getTooltip`, which calls the host's four-argument method with the client world's tooltip context, or the empty one where there is no world.

The 1.21.4 and 1.21.5 HUD layers take the vanilla `LayeredDraw.Layer`, which 26.1 removed. It becomes the shared `LegacyHudLayer`, as R1 handles `BlockColor`; `IdentifiedLayer` becomes `LegacyIdentifiedLayer` with a per-mod bridge for classes, and `LayeredDrawerWrapper` becomes `LegacyLayeredDrawerWrapper`, served by `LegacyHudLayers.Wrapper` over the host `HudElementRegistry`. The old registration event fires once at `ClientLifecycleEvents.CLIENT_STARTED`, after every mod's client setup, as Fabric API fired it while the client built its HUD. Ids that moved go to `VanillaHudElements`. Ids 26.x removed land where they stood. A layer before `HOTBAR_AND_BARS` goes before the spectator menu and one after it goes after the info bar, before the experience level that followed it in 1.21.4; removing it removes the ten elements it became, and replacing it replaces the hotbar. `STATUS_EFFECTS` is `MOB_EFFECTS`. `DEBUG`, the debug overlay that 26.x draws outside the element tree, places a layer before the scoreboard or after the demo timer, and removing or replacing it does nothing and logs once. javac writes a constant read without its type, inside a class that implements `IdentifiedLayer` or through a sub-interface, with the subtype as the owner; such a read goes to the same place when the jar's own classes prove the hierarchy. The same mapping serves 1.21.6 to 1.21.8 mods that pass `VanillaHudElements.DEBUG` to `HudElementRegistry`, because the runtime sends the four registry calls that take an anchor through `LegacyHudLayers`, which passes every other id to the host unchanged.

`GatherDebugTextEvents` becomes `LegacyDebugText`, and its `Left` and `Right` callbacks shared types. Fabric API 26.1 to 26.3 widen vanilla `DebugScreenEntries.register`, so the runtime adds one debug screen entry, `retromod:legacy_debug_text`, which shows each old column as one group. Like every 26.x mod entry it stays off until the player turns it on in the debug options screen, and the debug screen decides which column each group goes in. Fabric API 26.4 no longer widens that method; there the entry is added only if Minecraft made it public, which no local 26.4 jar could show.

Limits. The pre-1.20 `PoseStack` shapes of the HUD callback and both screen callbacks are impossible: 26.x draws screens and the HUD through `GuiGraphicsExtractor`, and Retromod's `PoseStack` drawing bridge, `LegacyPoseGui`, is embedded per mod and hands out pose stacks only for Forge-family render events. A HUD callback of that shape logs once and does not draw. A screen callback of that shape still fails with `AbstractMethodError` when the screen renders, as it did before the runtime; a real fix needs a per-mod pose adapter in front of the bridge. A dedicated server has no GUI classes, so a HUD lambda cannot be built there, as on 1.21.1; old mods register HUD callbacks on the client. Every S1 row except the four tooltip rows stays linked until a client run (`Test45ClientHudAndScreenEvents` and the client half of `Test46ScreenShapesFrom121`). The 26.3 server runs show that the HUD, layer, debug text and anchor code links, and `Test46` ran the debug text events through their invokers there, but the host HUD, screens and debug screen exist only on a client. An in-game client has not checked any S1 drawing yet. A constant read through an `IdentifiedLayer` subtype that another jar declares is not proven and still fails with `NoSuchFieldError`; no corpus mod uses `IdentifiedLayer`. Of the S1 corpus, Iceberg, OptiGUI and Sodium Extra translate with no Fabric API reference left on 26.3, as do the 1.20.1 Entity Culling and 3D Skin Layers with their nested TRender, and SpruceUI inside Enhanced Block Entities. Cherished Worlds still builds lambdas on the old `ScreenMouseEvents$AfterMouseClick.afterMouseClick(Screen, double, double, int)` and `AfterMouseRelease` methods (batch S2), so its first click in a screen it hooks fails with `AbstractMethodError`. The 1.21.1 Entity Culling and 3D Skin Layers nest TRansition, which reads `PayloadTypeRegistryImpl.PLAY_C2S` and `PLAY_S2C`, internal Fabric API fields 26.x renamed. Enhanced Block Entities itself still has model loading and renderer references (batches D1 and D2).

## Attribution

Adapted Fabric API files keep the upstream Apache-2.0 header plus one line naming the module, path and version, and are listed in `THIRD_PARTY_NOTICES.md`. `ThirdPartyAttributionTest` checks both directions.

## Open Items

- Measuring which mods depend on old transitive access widener entries (batch A1) needs the usage scanner extended; B0 did not do it.
- `isModLoaded("fabric")` and removed module ids in `getModContainer` still need a row family (critique finding 9).
- The link check reports a member as unknown when its owner's supertypes leave Fabric API, such as `TransferVariant` implementing a Minecraft interface.
- A class whose frames cannot be recomputed ships as written, apart from the class moves `SyntheticEmbedder` applies. This happens on the runtime and CLI paths with the runtime on or off, as in the baseline. In the S1 corpus that is Iceberg 1.20.1's `Tooltips`, SpruceUI's `SpruceEntryListWidget` and two Sodium Extra 1.20.1 mixins. Their Minecraft member calls keep intermediary names, such as `Minecraft.method_1551`, which the link check does not read.
- A mixin aimed at a Fabric API class the runtime redirects to a Retromod type (the N1 handler types, `FabricPacket`, `PacketType`) is not dropped yet. No corpus mod has one.
- `ServerConfigurationNetworking.createS2CPacket(CustomPacketPayload)`, renamed `createClientboundPacket` in 26.1, belongs to N2. Forge Config API Port 21.1.6 calls it.
